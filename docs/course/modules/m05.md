# Module 5 — VRF Deep Dive and Multi-Tenant Isolation

Scenario reference: [case study module m05](../case-study.md) · build outputs:
[policy-tenant-ai](https://github.com/shsingh/ai-infra-for-neteng/blob/master/PLAN.md#6-manifest-specifications) · guide: `docs/labs/lab04-tenant-isolation.md` (produced in build stage 9).

## Scenario

**Situation.** VRF with API-based dynamic routing per tenant is now generally available in
2.4, with per-tenant ACL enforcement on top — previously it was an Early Access path the
course could only describe.

**Request.** Give the tenant-ai VRF its own dynamic routing configuration and its own
ingress/egress ACL policy, matching the treatment every other tenant class already gets
from the campus fabric.

**Success criteria.** Cross-tenant traffic is blocked at the VRF boundary and visible in
the log stream; tenant-ai routing toward the spine still works; the MPLS
provider-edge capability (Early Access, not announced in the current release notes) is
correctly documented as out of scope.

## What changed (the GA promotion)

VRF support with API-based dynamic routing per tenant was Early Access previously; it is
**generally available** now, with per-tenant ACL-based ingress and egress policy
enforcement built on top. That promotion moves this from "demo, do not build" to a real
module: the tenant-ai VRF gets dynamic routing configuration and its own ACL policy,
matching how the campus fabric treats the other tenant classes.

## Content

- One data plane, many routing domains: VRF-per-tenant maps route domains the L3VPN way
  without separate boxes — the Module 4 pattern, now with dynamic routing per tenant.
- Per-tenant ACL enforcement: ingress and egress ACLs attach at the VRF/tenant boundary —
  the control that keeps industry-partner traffic from touching research systems (the
  Module 13 groundwork).
- The MPLS-PE status footnote (stated plainly): the MPLS provider-edge capability (label-based forwarding)
  is an Early Access path from the previous release and is not announced in the current
  release notes — verify status with the F5 account team. Map it to L3VPN concepts (VRF ->
  VPN label; EVPN overlay vs MPLS transport), and mark it explicitly: nothing in this
  course depends on it.

## Lab treatment (hands-on part of Module 4's flow)

1. Apply the tenant-ai ACL policy: `kubectl apply -f manifests/bgp/policy-tenant-ai.yaml`
   (per-tenant ingress/egress ACL attached via SecPolicy).
2. Test the isolation: cross-tenant curl from the teaching tenant's pod to the AI VIP ->
   blocked (observe the log stream); tenant-ai toward the spine -> still fine.

## Planes check

VRF + per-tenant ACLs = control-plane decisions (routing domains, policy computation)
enforced as data-plane state (separate tables, ACL drops) from a management-plane
declaration (the composite CRs).
