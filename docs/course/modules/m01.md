# Module 1 — Kubernetes for Network Engineers

Scenario reference: [case study module m01](../case-study.md) · build outputs in [PLAN](https://github.com/shsingh/ai-infra-for-neteng/blob/master/PLAN.md#4-repository-layout) ·
guide: `docs/labs/lab01-kubernetes.md` (produced in build stage 9).

## Scenario

**Situation.** A network engineer joins the Meridian AI platform team. The platform runs on
Kubernetes; the engineer has never managed one.

**Request.** "Get oriented on the platform" — build working familiarity with the Kubernetes
object model and locate every running component on the three planes.

**Why it matters.** Kubernetes has no console port and no per-device CLI: the management
plane is kubectl against the API server, and everything downstream of Module 1 assumes that
reflex.

**Success criteria.** The attendee can inventory nodes and pods, read a node's capacity
sheet, exec into the TMM pod, and diagnose the most common Kubernetes networking fault —
a Service selector mismatch — unaided.

## Lecture targets (concept talk, taught through the planes)

1. The object model as a tour of the management plane: pods (the line-card process),
   deployments, Services, namespaces, nodes. The headline: kubectl is not a config tool,
   it IS the management plane — every get/describe reads desired-versus-observed straight
   off the API (the merged `tmsh list` / `tmsh show` view), and every change enters the
   same way. Namespaces are the partition analogue (the ACI-tenant/Azure-tenant boundary);
   label selectors are match criteria; a Service is an LVS-style virtual with endpoints
   from labels. Establish the reflex now: nothing to configure exists outside the API.
2. The networking stack: what the default data plane can and cannot do. Pod IP per pod (no
   NAT in-cluster), CNI (Calico in this lab) as the underlay, kube-proxy vs eBPF, Service
   vs pod network, cluster DNS. Two data planes will coexist all day: the commodity pod
   plane (kube-proxy + CNI, fine east-west) and the hardware-grade forwarding engine
   arriving in Module 3 (the north-south edge). Name both now.
3. CRDs vs built-in resources: the management plane is extensible. Show one real F5 CR
   from the repo (`kubectl get crds | grep f5`, then read a routing CR): a CR is a resource
   type an operator added — new config nouns in the same management plane. This preview
   makes Module 4's YAML feel like a language already started.

## Hands-on (student track)

> Seat access: each instance is booted fresh at course start and reached over SSH, a web
> terminal, or a console — the steps are identical on every access path. Enter the pinned
> shell first (`nix develop`); the full bootstrap flow is specified in
> [PLAN §8.2](https://github.com/shsingh/ai-infra-for-neteng/blob/master/PLAN.md#82-bootstrap).

1. `kubectl get nodes -o wide` — two nodes: one control-plane+worker, one dedicated TMM
   worker. Read it like an inventory: name, status, role, version.
2. `kubectl get pods -A` — find the F5 pods by name (f5-tmm, f5-tmm-routing,
   f5-cne-controller, IPAM, observer). These are the "devices."
3. `kubectl describe node <tmm-worker>` — read allocatable like a capacity sheet (CPU,
   memory, hugepages if present).
4. Console into the line card: `kubectl exec -it <f5-tmm-pod> -c f5-tmm -- /bin/sh` —
   look around, then exit.

## Break-fix drill (attendee-executed)

The attendee applies fault `m1-endpoints` on their own instance
(`nix run .#break-fix -- m1-endpoints apply`), which deletes a Service's selector label,
and then diagnoses the effect: `kubectl describe svc` shows `Endpoints: <none>` — the most
common Kubernetes networking bug. The restore step (`restore` instead of `apply` on the
same command) closes the drill. Timing is the facilitator's call: if the lecture has run
long, the drill is presented as a demonstration instead — endpoint debugging repeats in
every later module.

## Planes check

The whole module lives on the management plane: kubectl talking to the API server is the
new SSH/tmsh. Attendees have touched no control or data plane yet, and should say so.

## Exit criteria

The student can explain the pod IP / Service / VIP difference and debug a label-selector
mismatch unaided.
