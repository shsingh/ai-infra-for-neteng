# Module 11 (Optional) — Can Open Source Do This?

Reads against: [case study](../case-study.md) work order m11 · guide: `docs/labs/lab10-oss-vs-bnk.md` (produced in build stage 9). No cluster work.

## Narrative beat

The CIO leans back: "Kubernetes is free, Envoy is free, Cilium does L4 load balancing —
why am I signing a purchase order?" This module is the engineer's answer, built honestly,
row by row.

## Method

For each row of the table below, the class first defends the OSS option, then the
the facilitator presents what the commercial platform adds. The summary line attendees should be
able to deliver: "OSS covers the commodity layers; buy where LTM-grade forwarding,
carrier protocols, hardware offload, or operational support are the requirement — and
nowhere else."

**Table 1: capability walk**

| Capability | The OSS baseline (what it does well) | Where it stops — and the commercial add |
|---|---|---|
| Pod networking / cluster L3-L4 | Calico/Cilium: excellent pod networking, NetworkPolicy, eBPF | Pod-level only. The commercial plane is a hardware-grade L4-L7 edge: full proxy architecture (VIPs, SNAT, iRules), DPU offload, NUMA/SR-IOV discipline for carrier-grade latency |
| Ingress (HTTP/S) | NGINX/Envoy/Kong + Gateway API: mature, free | Commodity HTTP ingress genuinely does not need the commercial plane — say so. The edge: LTM-grade L4-L7 features (rich SNAT/egress identity, firewall policies, iRules subset) consolidated with the same security tooling the estate already runs |
| East-west microsegmentation | NetworkPolicy/Cilium: strong, free | A different job (inside the cluster); the commercial plane is the north-south edge — these compose, not compete |
| BGP/EVPN/VRF programming | Cilium BGP / FRR solutions: peering works | The full routing-stack story: OcNOS with BGP unnumbered, EVPN, BFD inside the LB data plane, plus VRF/VXLAN purpose-built for tenant isolation — L3VPN-grade multi-tenancy at the edge |
| MPLS L3VPN provider edge | No mainstream OSS ingress does MPLS-PE | Early Access path only; honest row: watch this space |
| AI-era routing (cache-aware) | The Gateway API Inference Extension + its EPP: open, standard, genuinely good | The commercial add is not a replacement of the GAIE model: the declarative lifecycle (controller-rendered per-pool stacks), edge enforcement (DDoS/ACL/TLS) at the AI VIP, semantic caching (EA), token governance — with a supported, licensed data plane under the ext_proc traffic. Pattern: OSS control intelligence + commercial data-plane edge + lifecycle |
| Telco protocols (SCTP/NGAP/GTP/Diameter) | Weak or absent in OSS proxies | First-class CRs — for the telco estate this alone justifies the platform; for a university AI platform it is a non-driver, and the course says so |
| Observability & ops | Prometheus/Grafana + kubectl: sufficient for a skilled team | Adds device-level diagnostics and support workflows, fleet/drift/upgrade gating; buy-vs-build trade on operational surface |
| The existing F5 estate | — | Same TMM codebase and operational model as the LTM fleet already run: one skills base, one support line. For an existing LTM shop this is often the deciding row |

## Lab treatment

A structured argument exercise, not a slide show: split the room, half defends
"OSS-only for the AI platform," half defends "commercial at the edge," both using the
planes model and the day's configurations as evidence. Debrief: the defensible answer for
Meridian is hybrid — OSS control intelligence (Gateway API + EPP steering) with a
hardware-grade data plane at the edge, VRF-isolated per tenant. If a student can argue
where the commercial platform is NOT needed, they have learned the most transferable
lesson of the course.

## Planes check

The table itself is a planes exercise: the rows split into data-plane capability,
control-plane intelligence, and management-plane surface.
