## Narrative beat

The model pool is live; the platform team deployed round-robin load balancing. Time to
first token is poor under load and cache hit rates are near zero, and the researchers are
complaining their funded GPU hours are being wasted. Why? (Answer, from Module 2 and the
[KV-cache lesson](../planes-and-analogies.md#the-kv-cache-lesson-why-ai-load-balancing-is-not-http-load-balancing):
the control plane cannot see cache state.)

## Setup — the model pool

Deploy 3 replicas of the vLLM-protocol simulator ([llm-d-inference-sim](https://github.com/llm-d/llm-d-inference-sim);
zero GPUs, deterministic timing) in the pool namespace, labeled for pool membership
(`app: vllm-sim`); confirm the same OpenAI API on every pod. Three identical-looking
forwarders — the invisible difference (KV-cache contents) is exactly the control-plane
gap Module 2 predicted.

Prerequisites (2.4-specific cluster prep, verified by doctor): the GAIE v1.4.0 CRDs
applied; a GatewayClass/Gateway with Programmed=True; the pool namespace listed in
`CNEInstance.spec.eppNamespaces`; KV-event publishing enabled on the simulator pods.

## The problem (demonstrate, do not assert)

`nix run .#m8-blast` — a fixed prompt corpus with shared prefixes through the plain
Gateway: watch per-pod request counts spread evenly and cache hit rate near zero. Frame
in planes language: the current control plane computes its decision from packet headers
and Service membership — structurally blind to the application state that determines
performance.

## The fix — the three-CR path (nothing is hand-built; the controller renders the picker stack)

1. Apply `manifests/08-f5epp.yaml` — the F5EPP CR (engine preset `vllm`, poolRef
   `llm-pool`). Verify the cascade: `kubectl get f5-epps -n ai-inference` -> Accepted ->
   ResolvedRefs -> Programmed -> Available all True; pods and Service named
   `<pool>-epp*` (9002 ext_proc, 9003 health, 9090 metrics).
2. Apply `manifests/09-inferencepool.yaml` — selector on the sim pods, targetPorts 8000,
   endpointPickerRef -> the EPP service, `failureMode: FailClose` (a gateway that fails
   closed beats one that silently degrades into round-robin; argue FailOpen only for an
   availability-first platform — Module 13's design discussion).
3. Apply `manifests/10-httproute-inference.yaml` — the HTTPRoute parentRef to the Gateway;
   backendRef kind InferencePool (not Service — this is what activates steering). One
   InferencePool per rule, no mixed backends.

Naming contract: everything `<pool>-epp*`; all three CRs live in the pool namespace;
`poolRef` is immutable — repointing means delete + recreate (the Module 4 lesson
echoing).

## Verify — tmctl in the TMM debug container (the first "show commands" for AI routing)

```
kubectl -n <bnk-ns> exec -it <tmm-pod> -c debug -- bash
tmctl -d blade inference_stats        # intercepted vs passthrough vs misconfigured
tmctl -d blade inference_epp_stats    # schedule calls/successes/fallbacks, latency in microseconds
tmctl -d blade profile_ext_proc_stat  # the <ns>-llm-pool-epp-ivs row proves TMM<->EPP attachment
tmctl -d blade profile_http_stat      # 2xx/4xx/5xx per virtual server
```

Expected: requests_intercepted advancing; schedule_successes == schedule_calls; the
epp-ivs row non-zero; no fallbacks, errors, timeouts; consult latency well under one
millisecond. Prometheus side (port-forward the EPP service to 9090): GAIE-conformance
`inference_*` metrics plus the F5 families — `kv_event_lag`, `prefix_index_rebuild_lag`,
`prefix_index_lookups` (hit rate), `hcl_pod_classification` (HOT/COLD pods),
`scorer_score`. Rising event lag is the early warning.

Then `nix run .#m8-blast-again`: per-pod counts converge on cache-consistent targets and
TTFT variance collapses. Explain in LTM terms: adaptive persistence.

## Engine paths and tuning (the take-home tour)

| Engine | spec.engine | Extra required | KV-event transport | Default metrics scrape port |
|---|---|---|---|---|
| vLLM | vllm | — | ZMQ | 8000 |
| NVIDIA Dynamo | dynamo | spec.natsURL (required) | NATS | 9090 |
| SGLang | sglang | — | ZMQ | 30000 |

Same picker and scoring for all three — only the plumbing differs. Tuning take-homes:
aggregated vs disaggregated pool mode (only with labeled prefill/decode groups),
blockSize matching the engine, tokenizer pinning options, refresh interval trade-off,
and the eppConfig escape hatch (thresholds, scorer TTL, hot threshold).

## The other AI feature: semantic caching (Early Access — demo only)

A Gateway annotation bridging to an external cache service, supporting completions
endpoints (streaming supported). Demo + take-home only; no lab exercise depends on it
(the standing honesty rule), and a multi-tenant design must include tenant identity in
the cache key (Module 13's discussion). Position it honestly: the platform team owns the
edge (security, egress) and the picker (steering); the cache is a third layer, separate
job.

## Break-fix drills

  endpoints empty -> selector.
- `m8-pool-ports`: targetPorts do not match the sim's containerPort — the EPP picks an
  endpoint but requests fail. Trace the port path + `profile_http_stat` 5xx.

## Planes check

Module 8 installs a new control-plane function (the picker, at L7) beside the existing
control planes — it steers the data plane per request using state only the application
has (the KV cache), declared on the management plane (three CRs). The 2.4 change is
operational, not architectural: the declarative surface consolidated to one CR.
