## Narrative beat

The flagship pool went into production as a paid shared service: three tenant classes —
teaching, research, industry partners — bill against the same model fleet. The business
office asks: who meters each partner's consumption? The security office asks: what stops
one tenant (or the internet) from hammering the pool, poisoning the cache, or walking off
with another tenant's outputs? The platform team asks: how do we roll changes without
taking everyone's model offline? One module, three answers — all on the Module 8
architecture; nothing new to install except policies.

## The shared-model threat and cost model

A shared pool behind one Gateway differs from separate per-tenant pools:

- **Metering:** token consumption is the billable unit (GPU-hours track tokens), and it
  is invisible to IP-level accounting — one connection can carry ten tokens or ten
  million.
- **Fairness:** one tenant's bulk job can starve others (queue depth, cache memory — the
  scheduling lottery, weaponized).
- **Cross-tenant leakage:** prompts and results from tenant A must not become cache or
  steering signal for tenant B unless policy says so — with one shared pool, isolation
  comes from policy layers, not from separate clusters.
- **Abuse / DoS:** high-rate floods and token-stuffed prompts are the same hostile
  pattern aimed at two different targets: network capacity and cache memory.

## The control catalog (layer by layer)

| Control | Object / mechanism | What it decides |
|---|---|---|
| Tenant identity at the edge | SecPolicy/NetPolicy + iRule extraction | Who is asking (mTLS SAN, API key, egress zone) |
| Isolation between tenants | SecPolicy + FwPolicy/FwRulelist | Who may reach what; VRF/namespace per tenant class |
| Flood protection | DoS vectors + iRule | Connection floods, slow attacks, oversized requests |
| TLS/mTLS termination | Gateway/TLSRoute + GatewaySettings | Transport identity and encryption |
| Token metering + rate limiting | the `k8s.f5.com/ai-token-counting` Gateway annotation | How many tokens per identity, per model, per window; concurrent sessions |
| Prompt screening | Module 12's gate | What the prompt contains |
| Response caching | semantic caching (EA) + per-tenant keys | What can be reused vs must hit the model |
| Usage audit | HSL pools -> metering tools | Who used what — billing and forensics |

Notes behind the rows:

- **Tenant identity:** the edge already terminates TLS; the API key or mTLS identity is
  available per request the way it is on every LTM virtual server. Extraction: an
  `x-api-key` header or mTLS SAN — no sidecar, no proxy hop.
- **Isolation:** firewall policy gives the reachability matrix (tenant A may not initiate
  to tenant B); egress identity gives each tenant a nameable traffic identity (Module 7
  carried forward); VRF-per-class carries it into routing.
- **Flood/DoS:** DoS vectors shield the pool the same as any LTM virtual server; note the
  deliberate ordering — DoS runs below the picker consult (the Module 12 edge-ordering
  argument again: shield first, steer second).
- **Token metering + rate limiting** — the module's centerpiece. Annotation on the
  Gateway: token counting enabled; identity from the API-key header (source-IP fallback
  exists); policies per_user / per_model / per_user_per_model / global; per-window token
  budgets with separate input/output accounting; a concurrent-sessions cap per user;
  action = drop (429) or log_only; usage exported via HSL to metering tooling — the
  billing feed exists without any scraper. LTM mapping: a credential-identified rate
  shaping policy where the meter counts tokens and the identity is the API key, with the
  429 as the firewall-reject muscle memory. The seed configuration is
  [specified in PLAN](https://github.com/shsingh/ai-infra-for-neteng/blob/master/PLAN.md#62-token-counting-annotation-m13-anchor).
- **Prompt screening** — Module 12's gate, scoped per tenant class (partner traffic
  screens every request; the teaching tier can flag-only).
- **Usage audit** — HSL carries the 429s, verdicts, and token rows to the metering tool;
  the Observer CRD adds per-tenant statistics isolation (tenants scrape what they need,
  with no overlap — generally available in 2.4).

## Hands-on — meter and enforce the shared pool

1. Annotate the Module 8 Gateway: `kubectl apply -f
   manifests/14-token-governance-gateway.yaml` (the seed budget: teaching 50k tokens per
   hour, research 100k per hour, partners 100k per day, a global daily backstop,
   concurrent_sessions_limit 5, drop on breach).
2. The metered-vs-unmetered test: the same prompt with two different `x-api-key` values;
   compare the per-user token rows in the HSL stream (`nix run .#m13-hsl-tail`).
3. The breach test: `nix run .#m13-breach` drives a teaching-tier key past its hourly
   budget — watch the 429s arrive; confirm log_only keys keep flowing.
4. Per-tenant reachability: `kubectl apply -f manifests/15-m13-tenant-fw.yaml` — then the
   cross-tenant curl matrix (teaching -> research: blocked; teaching -> pool: allowed).
5. Billing rehearsal: one HSL row -> a metering record — the billing-evidence chain from
   the data plane to an invoice (facilitator demo).

## The per-policy walkthrough (the drill script)

1. per_user: one shared budget across everything a user touches.
2. per_model: all users of one model share a model-level pool (careful: a few heavy
   users can exhaust it for everyone).
3. per_user_per_model: the fair-split default — the seed configuration above.
4. global: one budget for all users — the circuit-breaker for cost blowouts.
5. concurrent_sessions on top of all of the above — the anti-stampede cap.

Then the design question every deployment answers once: identity at the edge (API key vs
mTLS SAN vs IP fallback) and the threshold behavior — drop (429) vs log_only
(measure-first is the recommended rollout: measure in log_only, then flip tiers to
drop).

## Planes check

All controls are declared on the management plane (annotations, policy CRs), decided per
request (inline), enforced by the edge with data-plane state (sessions, counters, 429s),
and audited by streaming the same decisions to HSL. New for 2.4: the Observer CRD
(per-tenant stats, no overlap) and the token-governance annotation as the
metering/enforcement point.
