## Narrative beat

The fabric team needs the AI cluster in the routing domain — same as every other site.
This is the module that converts skeptics.

## The routing-stack story (the module's spine)

The forwarding pod's routing container runs an OcNOS-class routing stack; TMM forwards.
Walk the config path naming the plane at every hop:

management plane (the CRD, YAML in Git) -> the CNE controller renders the Go template
(RoutingTemplate) -> gRPC/mTLS to the config watcher -> control plane (the routing CLI
configures eBGP/iBGP, BGP unnumbered, EVPN, BFD) -> netlink/protobuf programs the TMM
forward table. Three things to land: the protocols are the same ones running on the
campus spine today; the plumbing (CRD -> template -> gRPC -> CLI) is the only new
segment; and recognizing which control-plane plumbing you are on (legacy ConfigMap
method vs the current one) is a career skill in this space.

## Hands-on part 1 — global BGP (follow the documented order: template, then globals)

1. Read `manifests/bgp/routing-template.yaml` end to end — a Go template emitting routing
   CLI. This is `load sys config from-terminal` in a new skin: a complete config text
   merged by a controller.
2. Apply in order:
   ```
   kubectl apply -f manifests/bgp/routing-template.yaml
   kubectl apply -f manifests/bgp/global-routing-config.yaml
   kubectl get globalroutingconfig -o jsonpath='{.items[*].status.conditions}'
   ```
   Wait for success — do not move on early. ASN 65001; the spine neighbor is
   198.51.100.10, remote AS 65110.
3. Read the delivered config: where the rendered CLI lands; `kubectl logs` on the routing
   container.
4. The other side of the session: `nix run .#m4-bgp-verify` execs into the fabric spine
   container and runs `show bgp neighbor` / `show bgp ipv4 unicast` — confirm Established
   and routes exchanged. Students get the two-sided view they are used to.

## Hands-on part 2 — tenant VRF + VXLAN/EVPN

1. Apply the tenant declarations on the composite Infra CRD:
   ```
   kubectl apply -f manifests/bgp/vrf-tenant-ai.yaml
   kubectl apply -f manifests/bgp/vxlan-tenant-ai.yaml
   kubectl apply -f manifests/bgp/routing-config-tenant-ai.yaml
   ```
2. Re-read the tenant RoutingConfig: `vxlanRef` XOR `vrf` — the mutual exclusion is a
   schema rule.
3. Advertise the future VIP into the fabric (Module 6 makes the VIP exist; BGP
   advertises it — the sequence mirrors real projects).
4. Verify: routes in the spine container, BFD session state, CRD status fields on both
   ends.

Facilitator framing: one VRF + VXLAN pair per tenant class is how the university keeps
teaching, research, AI, and industry tenants out of each other's routing tables — the
L3VPN discipline, expressed as CRs.

## The immutability lesson

All five routing CRDs are immutable after creation — change = delete + recreate. Drill:
`kubectl patch` the ASN, watch it fail, then delete + recreate properly. Then quantify the
blast radius with the room: the delete is instant and the recreate takes effect only
after the new CR reconciles — between the two, the VIP and its BGP advertisements can
leave live traffic. In the lab it is a VIP they have not built yet; in production it can
be a tenant edge. The lesson: the safety check moves from apply-time to review-time —
that is what Git review and maintenance windows are for.

## Break-fix drills

- `m4-bgp-secret`: the neighbor Secret is corrupted; CRD status says success but BGP is
  idle. Diagnose from the spine: `show bgp neighbor` -> auth failure -> fix the Secret.
- `m4-vxlan-vni`: a VNI mismatch between the VXLAN CR and the spine bridge: route
  present, no east-west traffic — compare VNIs.

## Planes check

Control plane end to end: routing protocols running in the routing container, programmed
from the management plane (CRDs), feeding the data plane (forward table). Same protocols,
same planes — only the programming language changed; and the immutability drill shows
where the management plane's safety lives (Git review before anything moves).
