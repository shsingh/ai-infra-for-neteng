## Scenario

**Situation.** The GPU cluster hardware is approved and racked. The platform software
(BNK 2.4) must be installed, and it is the first platform install in the estate with no
tmsh.

**Request.** Install BNK in demo mode on the lab cluster, choose host vs DPU placement
with justification, and record what demo mode omits so the production design (including
the OpenShift requirement for BNK Host) is not inherited by accident.

**Success criteria.** The TMM pod is Ready, the CRD inventory is the acknowledged
management-plane surface, and the attendee can state which planes install changes.

## Theory (what an install actually installs — three planes, one chart)

- Data plane being installed: TMM — the hardware-grade forwarding engine, as pods. On
  hosts, TMM runs on host CPUs; on DPUs, TMM runs on the BlueField card and the host is
  freed for applications. Same TMM either way — a placement decision, not an architecture
  change.
- Control plane being installed: FLO (lifecycle), the CNE controller (config
  reconciliation), FIC (VIP allocation) — the controllers that compute desired vs observed
  for everything built later. In 2.4 the CNE controller also renders the EPP stack per
  pool.
- Management plane being installed: the CRD surface itself — the GatewayClass and
  CNEInstance drive installation; the same surface carries Modules 4–8 configuration.

## Hands-on (student track)

1. Each attendee bootstraps their own instance (started fresh when they arrived):
   `nix run .#bootstrap` (resume-safe — an interrupted run re-enters cleanly). Watch
   `kubectl get pods -A` come up and, for each pod, identify its plane (forwarding = data;
   controllers = control; the CRD inventory = management) against the component list.
2. `kubectl get bnkgatewayclass` and `kubectl get crds | grep -E "f5|inference"` —
   connect the CRD names to what was just installed: this is the management-plane
   inventory. Read one CR aloud as a config stanza — `router bgp` in YAML; the
   IOS/Junos-stanza habit transfers directly.
3. Demo-mode callout: what demo mode fakes (virtio; no SR-IOV, HugePages, Multus NADs)
   and what changes on real hardware (real interfaces in the Infra CRD VLAN sections,
   DPU offload). In planes language: demo mode swaps the data plane's physical attach;
   control and management planes are untouched.
4. Verify: `kubectl get pods` until TMM is Ready; the CRD inventory is the deliverable.

## DPU segment (demo/slides, never hands-on)

The DPU placement flow with device integration; where TMM runs; what the host sees. The
the facilitator presents captured output recorded from a real run (attendee environments are not involved).

## Break-fix drill

Fault `m3-scheduling`: a wrong `app=f5-tmm` nodeSelector leaves the TMM pod Pending;
attendees trace `kubectl describe pod` -> FailedScheduling events. Diagnose it as a
data-plane placement failure: the control plane scheduled the pod; the data plane has
nowhere to land.

## Planes check

Installing = installing a data plane (TMM) plus control-plane plumbing (CNE, FIC, FLO)
plus the management-plane surface (CRDs). The DPU model moves where the data plane
physically runs; the CRDs stay identical.
