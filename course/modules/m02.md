## Narrative beat

Why is the AI platform not on VMs behind the BIG-IP like everything else?

## Content (organised by plane, because that is the argument)

- **Data plane (the traffic):** inference traffic shapes — prefill vs decode, and the two
  numbers that matter: time to first token (TTFT) and inter-token latency (ITL). KV cache
  as the scarce resource ([the KV-cache lesson](../planes-and-analogies.md#the-kv-cache-lesson-why-ai-load-balancing-is-not-http-load-balancing)):
  cache memory outstrips CPU as the binding constraint, and prefix-aware scheduling is
  essential for production performance. East-west GPU chatter (RDMA/NVLink physics) vs
  north-south client traffic — two data planes with opposite physics on one cluster.
- **Control plane (the gap):** GPU scheduling is a Kubernetes-native problem (device
  plugins, `nvidia.com/gpu` resources, gang scheduling). But the scheduling problem the
  network team will own is request routing: round-robin fails because two
  identical-looking pods are not identical (KV-cache contents differ), and no
  packet-header control plane can see that difference. That is the hole Module 8 fills.
- **Management plane (the ask):** whatever fills the gap must be declarable, auditable,
  self-serviceable — it must surface as CRs the platform team can apply, not as a black
  box. In 2.4 the answer is InferencePool + the F5 endpoint picker, declared as CRs.

## Planes check

The endpoint picker is a new control-plane function — it computes where traffic should go
from application state, not packet headers. File the thought: Module 8 installs one for
real.
