# Module 6 — Gateway API: from VIP to Route

Reads against: [case study](../case-study.md) work order m06 · build outputs:
[manifests 01–03](../../PLAN.md#6-manifest-specifications) · guide: `docs/labs/lab05-gateway-api.md` (produced in build stage 9).

## Narrative beat

The platform team wants ingress without filing tickets to the network team. The network
team needs to see what they will build.

## Concept bridge (open with the packet, not the API)

By the end of this module, one HTTP request will have crossed all three planes in order,
and the class will narrate every hop. Then the objects as the management-plane surface
that starts the walk: Gateway API = roles model (GatewayClass = infrastructure owner,
Gateway = VIP + listeners, Route = the application teams' rules). For this audience:
Gateway ≈ the virtual server object; listener ≈ VIP:port; Route ≈ the rule that picks the
pool. The F5 IPAM controller allocates VIPs. Cloud-native colleagues already speak this
shape (AWS ALB listener + rules; Azure frontend IP + LB rules); the one honest
difference: in the cloud the platform owns the load balancer — here the Gateway CR
programs TMM.

## Hands-on (narrate the planes while typing)

1. Deploy the demo app: `kubectl apply -f manifests/01-demo-app.yaml` (nginx + Service in
   tenant-ai) — two CRs, zero packets.
2. Create the ingress objects: `kubectl apply -f manifests/02-gateway-httproute.yaml`
   (Gateway + GatewaySettings + HTTPRoute). Management plane: the VIP is now a
   declarative object.
3. Find the VIP: `kubectl get gateway` (status address, allocated by FIC). Then
   `curl http://<vip>/` — the control plane computed the address, rendered the config,
   and the data plane is answering. Have a student say the three planes out loud, in
   order.
4. Attach an iRule the network way: `kubectl apply -f manifests/03-irule-cneirule.yaml`
   (the Irule CR + NetPolicy extensionRefs/targetRefs at the listener). Use a trivial
   log rule; note the validation webhook. The management plane carrying LTM-era logic
   into the new world.
5. Trace the config path from Module 4: CR -> controller -> gRPC -> TMM, end to end.

## L4Route in five minutes

L4Route serves TCP/UDP listeners — the workhorse for non-HTTP apps; constraints: TCP/UDP
only, one L4 route per listener. Product how-to:
[L4Route](https://clouddocs.f5.com/bigip-next-for-kubernetes/latest/custom-resource-definitions/bnk-gateway-api-l4route.html).
Tease Module 7.

## Break-fix drill

Fault `m6-route-ns`: an HTTPRoute lands in the wrong namespace — Gateway programmed, route
not attached. Diagnose: `kubectl describe httproute` -> parents empty -> move it.

## Planes check

One request crossed all three planes in order: management (the applied CR) -> control
(IPAM allocated, controller rendered, routing advertised) -> data (TMM forwarded). This
is the course's defining walk — students just performed it.
