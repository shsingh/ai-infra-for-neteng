# Module 10 (Optional) — bnk-forge, the Management Surface

Reads against: [case study](../case-study.md) work order m10 · guide: `docs/labs/lab09-bnk-forge.md` (produced in build stage 9).
Product: [bnk-forge](https://github.com/f5devcentral/bnk-forge).

## Narrative beat

Day-2 reality: the NOC wants a dashboard, the change-control board wants an audit trail,
the platform team wants deploy buttons — without anyone hand-writing CRs under pressure.

## What bnk-forge is

A self-hosted GUI (React/FastAPI) for deploying and operating the platform, talking to
clusters via kubeconfig. Day 1: deploy wizard, packaged blueprints, dependency-wired
execution. Day 2: traffic-flow visualization, health dashboards, multi-cluster fleet
view, drift detection, rolling upgrades with pre-checks and rollback, config
export/import, webhook alerting. Kubernetes/Helm surface: resource browsing, pod
logs/exec, Helm install/upgrade/rollback, node cordon/drain. Security posture:
role-based access (admin/operator/viewer), token auth, an audit trail on every mutating
operation.

Teaching frame (keep it honest): bnk-forge is a **management-plane surface** — the same
CRDs underneath. Everything typed in Modules 4–8 becomes a screen. It adds no data plane
and no control plane; its value is aggregation, visibility, audit, and safety rails —
the day-2 jobs that are awkward over raw kubectl for mixed-skill teams.

## Hands-on — point it at the lab cluster

1. The facilitator pre-starts bnk-forge on the lab host (needs only Docker and the bridge
   network).
2. Add the lab cluster: Clusters -> Add Cluster -> paste the lab kubeconfig.
3. Tour, tied to what the class built by hand: health dashboards (find the controller and
   forwarding-pod health); the traffic-flow view (find the Module 6 Gateway -> HTTPRoute
   -> nginx path); resource browser (open the Module 4 GlobalRoutingConfig); audit trail
   (find your own kubectl apply actions — and identify what it did NOT record).
4. Demo segment: the deployment wizard, plus drift detection against a second cluster —
   the facilitator edits a CR out-of-band and shows bnk-forge catching it.

## Discussion beat

When is a GUI right? Change windows, fleet views, mixed-skill teams, audit needs. When is
it wrong? Anything that skips Git review. The class should articulate: a GUI is a view
and control surface on the management plane, not a substitute for the declarative repo.
Note the license and maturity (openly licensed, community-maintained) before production
use.

## Planes check

Management-plane surface only — reads/writes the same API; zero data-plane or
control-plane function.
